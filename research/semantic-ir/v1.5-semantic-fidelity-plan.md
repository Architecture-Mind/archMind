# IR v1.5 — Semantic Fidelity Remediation Plan

**Status:** proposed, not yet implemented
**Motivating data:** `~/Desktop/DuckCode/TestFolder/FULL_BENCHMARK_REPORT.md` and
`REASONING_CROSSFILE_MULTITURN_REPORT.md` — every incorrect LLM answer across
4 benchmark rounds (factual retrieval, reasoning, cross-file, multi-turn), run
against 2 real Laravel projects (koel, BookStack) over ~20 questions, traced
to one of 6 concrete gaps below, not to retrieval reach, prompt quality, or
model capability. See `spec.md` for the shipped v1.4 type system this extends.

## Principle

**Scope of this claim:** the benchmark data supporting this plan covers Laravel
only (koel, BookStack), ~20 questions. It is not yet evidence that reachability
is a solved problem in general — a Spring Boot benchmark next could easily
surface its own reachability gap (e.g. AOP proxy indirection breaking
transaction-boundary resolution). The claim below is scoped to what was
actually observed, not generalized past it.

Across the benchmarked Laravel workloads, execution-graph traversal reached
the correct execution path in most cases — the graph got to the right node.
Retrieval reach did not appear to be the dominant limiting factor in this
sample. The remaining accuracy ceiling was primarily explained by **semantic
fidelity**: the node that was found didn't encode enough meaning for the LLM
to draw the right conclusion from it. Every phase below adds a
narrowly-scoped node type, edge relation, or node field — never a broad
redesign — so each is independently shippable, testable, and benchmarkable
against the same fixtures that exposed the gap. If a future benchmark (Spring
Boot, NestJS, or a larger Laravel sample) surfaces a genuine reachability
miss, that's new evidence and should reopen the reachability question rather
than being forced into a semantic-fidelity framing.

## Sequencing (by confirmed benchmark impact, highest ROI first)

| # | Gap | Confirmed impact | Effort |
|---|---|---|---|
| 1 | Middleware group resolution | 4/5 BookStack accuracy misses + 1 koel false-positive (5/10 in the factual-retrieval benchmark) | Medium |
| 2 | Mutation vs. reference | 2 misses (cross-file token-revocation, multi-turn turn 1) | Small |
| 3 | Transaction scope | 1 miss, but a *regression vs. baseline* (reasoning Q3) | Small |
| 4 | Guard clause / abort | 1 shared miss (multi-turn turn 4) | Medium |
| 5 | Audit / side-effect | 1 shared miss (multi-turn turn 5) | Small |
| 6 | Control-flow branch | 1 miss, most invasive to model | Large |

Do phases in this order. Each phase ends with re-running the specific
benchmark question(s) it targets against the real koel/BookStack repos in
`TestFolder` as a regression check — not just unit fixtures — since that's
what exposed the gap in the first place.

## Phase 1 — Middleware group resolution

**Root cause:** `parseRouteFile()` only parses the route file itself. When a
route file's middleware is applied by wrapping `require base_path('routes/api.php')`
inside `Route::group(['middleware' => 'api', ...])` in `RouteServiceProvider.php`
(the standard Laravel skeleton pattern), the parser never sees it — zero
`ir:auth_gate` nodes are emitted for the entire file. Conversely, a route file
that inlines `->middleware('api')` gets an `ir:auth_gate` node tagged from the
bare string `"api"`, regardless of whether `Kernel.php`'s `api` group actually
contains an authentication middleware or not (koel's `api` group doesn't; a
default Laravel skeleton's usually does via `ApiAuthenticate`/`auth:sanctum`).

**Fix:**

1. New parser module `packages/laravel-parser/src/route-service-provider-parser.ts`:
   parse `app/Http/Providers/RouteServiceProvider.php` (or `bootstrap/app.php` on
   Laravel 11+, which uses a different registration style — check both) for
   `Route::group(['middleware' => X, ...], fn () => require base_path(Y))`
   patterns. Output: `Map<routeFilePath, string[]>` (route file → middleware
   group names wrapping it).
2. Extend `parseKernel()` (already resolves `$middlewareAliases`/`$routeMiddleware`)
   to also parse `protected $middlewareGroups = [...]` and return
   `Map<groupName, string[]>` (group name → concrete middleware class list).
3. In `parseRouteFile()`, accept the resolved wrapping-group list for this file
   (from step 1) and the group→class map (from step 2 extension). For every
   route with no inline `->middleware()`, synthesize `ir:auth_gate`/other nodes
   from the *resolved concrete middleware classes*, not the bare group name.
4. Stop tagging a middleware node as `ir:auth_gate` purely because its string
   matches `/api|auth/`. Instead, classify by the **resolved class name**
   against an allowlist (`Authenticate`, `ApiAuthenticate`, `auth:sanctum`,
   `EnsureUserHasRole`-style aliases already in `parseKernel()`'s alias map).
   Unresolvable/unknown middleware strings get a new, honest node type —
   see `IR_NODE_TYPES.UNKNOWN_MIDDLEWARE` below — rather than a guessed one.

**Schema change (`packages/protocol/src/ir.ts`):**

```ts
UNKNOWN_MIDDLEWARE: "ir:unknown_middleware",  // resolved name but unclassified — honest "don't know" instead of guessing auth_gate
```

**Test fixtures:** add `RouteServiceProvider.php` + `Kernel.php` fixture pair
to `packages/laravel-parser/src/__tests__/fixtures/` replicating BookStack's
exact pattern (group wraps a `require()`'d file with `ApiAuthenticate` in
scope) and koel's exact pattern (group name `api`, no auth middleware in
scope) — these are the two real regressions found.

**Regression check:** re-run the factual-retrieval benchmark's 10 questions
(or at minimum the 6 that were wrong) against koel + BookStack; expect the
4 BookStack false-negatives and 1 koel false-positive to flip to correct.

## Phase 2 — Mutation vs. reference

**Root cause:** `$user->apiTokens()->delete()` is captured as a single
`ir:service_call` node with symbol `User::apiTokens` — the relationship
accessor is recorded, but the terminal `.delete()` chained onto it is
dropped. The LLM sees "apiTokens was referenced" and can't conclude
"...and therefore deleted."

**Fix:** wherever chained method calls are extracted into service-call nodes
(Laravel: the chain-walking logic in `route-parser.ts`/wherever
`transaction-parser.ts`/service-call extraction lives; NestJS: the
`service-call.extractor.ts` equivalent), detect a terminal mutating call in
the chain — `delete`, `update`, `save`, `create`, `attach`, `detach`, `sync`,
`forceDelete` for Laravel/Eloquent; adjust the allowlist per framework — and:

- Fold it into the node's `symbol`: `User::apiTokens()->delete()` instead of
  `User::apiTokens`.
- Tag the node with a new field so retrieval/prompt-building can highlight it
  distinctly without a whole new node type (keeps this a Small change):

```ts
// ExecutionNode (packages/protocol/src/graph.ts) — new optional field
mutates?: boolean   // true when this call terminates in a data-mutating operation
```

- `serializeExecutionPath` (prompt-builder) renders `mutates: true` nodes with
  an explicit `[MUTATES]` marker so the LLM doesn't have to infer it from the
  symbol string.

**Test fixtures:** extend the existing BookStack-pattern-derived fixture (or
add a new small Laravel fixture) with a relationship-accessor chain ending in
`.delete()`, `.save()`, and one that's *read-only* (`.get()`, `.first()`) to
verify the negative case doesn't get mistagged.

**Regression check:** re-run reasoning Q4 (cross-file token-revocation) and
multi-turn turn 1 against BookStack `DELETE /users/{id}`; expect both to flip
to correct.

## Phase 3 — Transaction scope

**Root cause:** `ir:txn_boundary` is emitted as a flat node in the traversal
list — the graph says "a transaction exists somewhere in this call chain" but
never says *which* other nodes are inside vs. outside its scope. The LLM sees
a `txn_boundary` node anywhere in the list and over-generalizes to "the whole
operation is atomic," which was directly wrong for `UserRepo::destroy()`
(the transaction belongs to a different, unrelated sub-call).

**Fix:** make containment explicit via edges rather than a new node type
(Small effort, matches existing `IR_EDGE_RELATIONS.WRAPS` which is defined
but check current usage — extend if underused):

- For every node structurally inside a `DB::transaction(function () {...})`
  closure (or NestJS `@Transactional()`/manual transaction manager block),
  emit an edge `{ from: txnBoundaryNodeId, to: containedNodeId, relation: IR_EDGE_RELATIONS.WRAPS }`.
- Nodes from sibling calls in the same method but *outside* the closure get
  no such edge — this is the critical negative signal.
- `serializeExecutionPath` renders wrapped nodes nested/indented under their
  `txn_boundary` node (e.g. an ASCII tree), and explicitly lists any
  mutating/write nodes that have *no* wrapping transaction, so "not
  transactional" is a visible, positive statement, not an absence the LLM has
  to infer.

**Test fixtures:** a fixture method with two DB writes, one inside
`DB::transaction(fn() => ...)`, one outside it in the same method — this is
exactly `UserRepo::destroy()`'s shape (tokens/social/favourites deleted
outside any transaction; only the deeper `ImageService::destroy` opens one).

**Regression check:** re-run reasoning Q3 (transaction rollback) against
BookStack `DELETE /users/{id}`; expect it to flip from incorrect to correct,
and re-verify Q3 doesn't regress into false "not transactional" claims on a
route that genuinely is fully wrapped (e.g. `RoleApiController::create`).

## Phase 4 — Guard clause / abort semantics

**Root cause:** `ensureDeletable()` (throws `NotifyException` if the target
is the last admin or the guest account) is captured as a generic
`ir:service_call` — indistinguishable from any other method call. The graph
has no way to say "this call can abort the whole operation based on a
precondition," so neither pipeline (archMind or baseline) catches
admin-deletion protection.

**Fix:**

**Schema change:**

```ts
GUARD_CLAUSE: "ir:guard_clause",  // a call that can short-circuit execution via throw/abort/early-return based on a precondition
```

```ts
GUARDS: "ir:guards"  // already exists (IR_EDGE_RELATIONS.GUARDS) — reuse: guard_clause node --guards--> the operation(s) it protects
```

**Detection heuristic (Laravel):** when resolving a called method's body
(parser already has file-resolution infra via `fqcnToPath`/`parse-cache.ts`
for cross-file lookups), classify it as a guard clause if:
- the method's first statement(s) are `if (cond) { throw ...; }` /
  `if (cond) { abort(...); }`, with no other significant logic before it, OR
- the method name matches a common guard-naming convention
  (`ensure*`, `assert*`, `guard*`, `verify*`) **and** its body contains a
  `throw`/`abort` reachable from an `if`.

This is explicitly a heuristic (documented as such, same posture as existing
"explicitly excluded patterns" in spec.md) — false negatives (missed guards)
are acceptable and safe; false positives (tagging a non-guard as a guard)
should be avoided by requiring the throw/abort to be structurally close to
the method's entry, not buried deep in unrelated logic.

**Test fixtures:** a fixture service method matching `ensureDeletable()`'s
exact shape (early `if / throw` pattern) and a fixture method that merely
*happens* to contain a throw deep inside unrelated logic, to verify the
heuristic doesn't over-fire.

**Regression check:** re-run multi-turn turn 4 (admin-deletion protection)
against BookStack; expect it to flip to correct for archMind (baseline has
no path to this fix since it never sees `UserRepo.php`).

## Phase 5 — Audit / side-effect semantics

**Root cause:** `Activity::add(ActivityType::USER_DELETE, $user)` is captured
as a generic `ir:service_call`, indistinguishable from a business-logic call.
Neither pipeline flags it as "an audit trail exists" because nothing marks it
as a side effect worth mentioning.

**Fix:**

**Schema change:**

```ts
AUDIT_LOG: "ir:audit_log",  // side-effect: a durable audit/activity-log record is created
```

**Detection:** pattern-match call symbols against a configurable "audit sink"
list — ship a small default list per framework (Laravel: `Activity::add`,
`activity()->log`, common package names like `spatie/laravel-activitylog`'s
`activity()` helper) plus a user-config override (mirrors the existing
`ArchMindUserConfig`/custom-decorator-registry pattern already used in
`nestjs-parser`'s `decorator.scanner.ts` for extensibility — same mechanism,
new list).

**Test fixtures:** a fixture service method calling a known audit sink
pattern, verifying it's tagged `ir:audit_log` instead of generic
`ir:service_call`.

**Regression check:** re-run multi-turn turn 5 (audit log question) against
BookStack; expect it to flip to correct.

## Phase 6 — Control-flow branch (request parameter → behavior)

**Root cause:** `$newOwnerId = $request->input('migrate_ownership_id', null);`
followed by `if (!empty($newOwnerId)) { ... } else { ... }` inside
`migrateOwnership()` is invisible to the graph entirely — there's no node
type for "this request parameter controls which branch executes," so the
entire ownership-migration-vs-nullification behavior is absent from the IR,
even though it's sitting in plain sight in the controller. This is the
largest, most invasive gap: it requires modeling control flow, not just call
targets.

**Fix (staged, not all at once — this is the "Large effort" item):**

1. **Narrow first cut:** detect the specific, common pattern of
   `$request->input(...)`/`->has(...)`/`->boolean(...)` feeding directly into
   an `if` condition within the handler or a directly-called service method.
   Emit:

```ts
CONDITIONAL_BRANCH: "ir:conditional_branch",  // execution forks based on a named condition
```
```ts
CONTROLS: "ir:controls",  // conditional_branch node --controls--> nodes that only execute in that branch
```

   Node `symbol` = the condition text (e.g. `!empty($newOwnerId)` or a
   normalized `migrate_ownership_id is present`), sourced from the request
   parameter name so it reads meaningfully without needing the source.

2. **Do not** attempt full CFG/SSA modeling in this phase — that's
   correctly identified in `discuss6.txt` as the long-term direction
   (Level 5: concurrency/isolation/retry/idempotency), but it's a
   multi-quarter investment, not a phase of this plan. Ship the narrow
   request-param-branch case first since it's the one the benchmark actually
   found; expand condition-source coverage (config value, header, role check)
   incrementally afterward, each as its own small addition once a benchmark
   or real project exposes the need — don't speculatively build coverage for
   conditions nothing has asked for yet.

**Test fixtures:** replicate `UserRepo::migrateOwnership()`'s exact shape —
request param → if/else → two different downstream calls.

**Regression check:** re-run multi-turn turn 2 (ownership reassignment)
against BookStack; expect archMind to flip from incorrect to correct,
matching what baseline already gets right by reading the file directly.

## Cross-cutting: Semantic Coverage metric

Per `discuss6.txt`'s proposal, track a **Semantic Coverage** percentage
alongside accuracy/tokens/latency/precision in future benchmark reports. Two
scopes for this metric:

**Narrow scope — the 6 gaps this plan targets** (how many now have a modeled
IR node/edge/field, tracked per phase landed):

| Semantic | Status after this plan ships |
|---|---|
| Middleware resolution | Phase 1 |
| Transaction scope | Phase 3 |
| Mutation vs. reference | Phase 2 |
| Guard clause / abort | Phase 4 |
| Audit / side-effect | Phase 5 |
| Control-flow branch | Phase 6 (narrow cut only) |

**Broader scope — the full semantic surface an execution-aware IR should
eventually cover**, extending beyond what this plan alone fixes. Categories
with no benchmark evidence yet are marked accordingly rather than assumed
solved or broken:

| Category | Coverage | Evidence |
|---|---|---|
| Authentication | ✅ modeled, gap fixed in Phase 1 | benchmarked |
| Authorization | ✅ modeled (`ir:authz_check`) | benchmarked |
| Transactions | ✅ scope fixed in Phase 3 | benchmarked |
| Mutation | ✅ fixed in Phase 2 | benchmarked |
| Side effects (audit) | ✅ fixed in Phase 5 | benchmarked |
| Control flow | 🟡 narrow cut only (Phase 6) | benchmarked |
| Async execution (queue/event) | 🟡 modeled (`ir:queue_job`/`ir:event_dispatch`) but sync-vs-async on the *listener* isn't surfaced distinctly (see reasoning benchmark, side-effects question) | benchmarked |
| Concurrency (race conditions) | ❌ not modeled — the race-condition finding in the reasoning benchmark came from the LLM reading node *symbols* (`firstOrCreate` + manual `++`), not from a dedicated IR concept | benchmarked, not yet modeled |
| Cache | ❌ not modeled | **no benchmark evidence — not yet tested, do not assume this is a real gap until a benchmark exercises it** |
| Distributed events (webhooks, cross-service) | ❌ not modeled | **no benchmark evidence — Laravel-only monolith fixtures so far, this needs a benchmark against a service that actually calls webhooks/external services before treating it as confirmed** |

Report the narrow-scope number (`N/6`) per release in the same place
`IR_VERSION` is bumped, e.g. "IR v1.5 — Semantic Coverage 5/6" — that's the
one backed by concrete, reproduced benchmark failures. Treat the broader
10-category table as a roadmap/tracking view, not a claim: rows marked
"no benchmark evidence" should stay that way until a benchmark specifically
targets them, rather than being silently promoted to ✅/❌ based on
assumption.

## Versioning

Bump `IR_VERSION` in `packages/protocol/src/ir.ts` once per phase that lands
(not all at once) — e.g. `"1.4" → "1.5"` after Phase 1, `"1.5" → "1.6"` after
Phase 2, etc. — so `adapter_ver`/`ir_ver` on emitted graphs stay meaningful
for regression-keying, matching the existing pattern already used for prior
IR domains (v1.1 Resource, v1.2 API Response, v1.3 Async dispatch, v1.4
Side-effect).

## What this plan deliberately does not do

- Does not touch NestJS or Spring Boot parsers in this pass — all 6 gaps
  were found via Laravel fixtures (koel, BookStack). Once Phase 1-5 land and
  are proven against Laravel, port the same node types to the other two
  adapters as a follow-up pass with their own framework-specific detection
  logic (NestJS: Nest interceptors/guards for guard-clause; TypeORM
  transactions for scope; etc.) — do not build speculative cross-framework
  support before a benchmark demonstrates the same gap exists there.
- Does not attempt full CFG/SSA/PDG modeling (`discuss6.txt`'s Level 5). That
  remains the long-term direction but is out of scope for a plan meant to
  fix 6 *specific, already-found* bugs.
